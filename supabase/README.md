# Как включить настоящую отправку SMS

Сейчас SMS не приходит не из-за приложения. В проекте Supabase
телефонная авторизация выключена и SMS-провайдер не подключён:

```
GET /auth/v1/settings → "external": { "phone": false }
```

То есть отправлять сообщение сейчас физически некому — ни в приложении,
ни на сайте. Нужно один раз подключить шлюз. Ниже два способа.

Приложение само определяет, что настроено, и переключается —
менять код клиента не нужно.

---

## Способ 1 (рекомендую): свой шлюз через Edge Functions

Подходит для России: sms.ru и smsc.ru работают с российскими номерами
и стоят порядка 3–5 ₽ за сообщение.

### 1. Таблица кодов

```bash
supabase db push
```

Или выполнить `migrations/20260910_phone_codes.sql` в SQL Editor.

Коды в базе не хранятся в открытом виде — только SHA-256 хеш с солью.
Клиентский ключ к таблице доступа не имеет.

### 2. Ключи провайдера

sms.ru — зарегистрироваться, получить `api_id`:

```bash
supabase secrets set SMS_PROVIDER=smsru
supabase secrets set SMSRU_API_ID=ваш_api_id
supabase secrets set SMS_FROM=DetiNaPlanete   # необязательно, имя отправителя
```

smsc.ru — вместо этого:

```bash
supabase secrets set SMS_PROVIDER=smsc
supabase secrets set SMSC_LOGIN=логин
supabase secrets set SMSC_PASSWORD=пароль
```

Для отладки без реальной отправки:

```bash
supabase secrets set SMS_PROVIDER=log
```

В этом режиме код не отправляется, а пишется в логи функции
(`supabase functions logs send-sms-code`). Не оставляйте `log`
в рабочем проекте. Если `SMS_PROVIDER` не задан, функция отвечает
ошибкой 503 и не делает вид, что SMS ушло.

### 3. Развернуть функции

```bash
supabase functions deploy send-sms-code --no-verify-jwt
supabase functions deploy verify-sms-code --no-verify-jwt
supabase functions deploy teacher-login --no-verify-jwt
```

`--no-verify-jwt` нужен потому, что код и пароль проверяются до входа
в аккаунт. Общие помощники функций лежат в `functions/_shared/`.

### 4. Проверить

```bash
curl -X POST 'https://<project>.supabase.co/functions/v1/send-sms-code' \
  -H 'Content-Type: application/json' \
  -H "apikey: $ANON_KEY" \
  -d '{"phone":"+79991234567"}'
```

Ожидаемый ответ: `{"sent":true,"codeLength":4,...}`.

После этого приложение при первом запросе кода само увидит функцию
и переключится в режим настоящей отправки.

### Что уже заложено в функции

* код 4 цифры, живёт 5 минут;
* не чаще одного SMS в минуту на номер;
* не больше 5 SMS в час на номер;
* не больше 5 попыток ввода, потом нужен новый код;
* код одноразовый: после успешной проверки повторно не принимается;
* хеш сравнивается за постоянное время;
* в базе только хеш кода, сам код не хранится и не возвращается клиенту.

## Способ 2: встроенная телефонная авторизация Supabase

Dashboard → Authentication → Providers → Phone → включить,
выбрать провайдера (Twilio / MessageBird / Vonage) и вписать ключи.

Ничего разворачивать не нужно: приложение увидит
`external.phone: true` и переключится на `signInWithOtp` / `verifyOtp`.

Минус для РФ: Twilio дороже и с российскими номерами работает
не всегда стабильно.

---

## Пока ничего не настроено

В сборке для разработки (`npx expo start`) приложение работает в режиме
`dev`: SMS не отправляется, подходит тестовый код `1234` (тот же, что
в веб-версии), а на экране ввода кода честно написано об этом.

В релизной сборке тестовый код отключён: без шлюза вход по номеру
недоступен. Для внутренней тестовой сборки его можно явно включить
переменной `EXPO_PUBLIC_ALLOW_TEST_OTP=true` — только не для сборки,
которая уходит в сторы.

## Безопасность

Приложение и сайт работают с базой по публичному (anon) ключу, а вход
проверяется на клиенте. Значит, всё, что разрешено ключу политиками
RLS, доступно любому, кто достал ключ из приложения или сайта.
Ниже — что стоит сделать на сервере, по убыванию важности.

### 1. Закрыть чтение паролей

После развёртывания `teacher-login` клиенту не нужен
`users.password_hash`. В `users`, по словам прежнего README, есть ещё
и `password_plain` — её нужно удалить совсем.

Колоночный `REVOKE` в Postgres не работает, пока у роли есть право
на всю таблицу, поэтому права выдаются списком колонок. **Перед
выполнением сверьте список с запросами сайта**: `select('*')`
по `users` после этого перестанет работать.

```sql
alter table public.users drop column if exists password_plain;

revoke select on public.users from anon, authenticated;
grant select (id, phone, first_name, last_name, avatar, bonus_points,
              is_phone_verified, is_active, role, created_at, updated_at)
  on public.users to anon, authenticated;
```

### 2. Настоящие сессии вместо «id в хранилище»

Сейчас «сессия» — это id пользователя на устройстве, а база
не знает, кто делает запрос. Надёжная схема:

1. `verify-sms-code` и `teacher-login` после успешной проверки выпускают
   JWT, подписанный секретом проекта (`sub` = id пользователя,
   `role` = `authenticated`, короткий срок жизни), либо заводят
   пользователя в Supabase Auth и возвращают его сессию.
2. Приложение хранит токен в защищённом хранилище (`expo-secure-store`)
   и передаёт его в заголовке `Authorization`.
3. Политики RLS проверяют `auth.uid()`: родитель видит только своих
   детей, записи и уведомления; преподаватель — свои занятия.
4. Анонимному ключу оставляют только чтение каталога
   (направления, расписание, тарифы).

Это общая переделка с сайтом, поэтому в приложении она не сделана.

### 3. Атомарные операции с балансом

Списание и возврат занятий делаются в два запроса
(прочитать → записать). При одновременной записи с двух устройств одно
списание может потеряться, а клиент с публичным ключом может записать
любое значение. Лучше вынести это в функцию базы:

```sql
create or replace function public.book_lessons(p_subscription uuid, p_count int)
returns int language sql security definer set search_path = public as $$
  update user_subscriptions
     set lessons_left = lessons_left - p_count
   where id = p_subscription and lessons_left >= p_count
  returning lessons_left;
$$;
```

(с проверкой владельца через `auth.uid()` после пункта 2).

### 4. Ограничение перебора пароля

`teacher-login` отвечает одинаково на «нет такого преподавателя» и
«неверный пароль», но число попыток пока не ограничено. Можно добавить
таблицу попыток по аналогии с `phone_codes`.
